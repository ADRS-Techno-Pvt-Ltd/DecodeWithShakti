## What this is

An LMS question-bank purchase platform (Phase 1), built to grow into a full-fledged LMS. See:

## Stack

- **Next.js 16** (App Router, TypeScript), no separate backend server — see "Next.js 16 specifics" below, this version differs from most training data
- PostgreSQL via Prisma ORM
- Cloudinary file storage (`src/lib/storage.ts`): question-bank PDFs/previews/thumbnails under `question-bank/<id>/`, invoices under `invoices/`. PDFs are uploaded as `type: authenticated` (raw) and only ever streamed back through the authenticated `/api/v1/files/**` route handlers; thumbnails are public images served straight from the Cloudinary CDN
- TanStack Query (server state) + Zustand (client UI state) — see `docs/HLD.md` § 5
- shadcn/ui (Tailwind v4, `base-nova` preset, indigo primary + custom success/warning tokens) — see `docs/HLD.md` § 6 for the design system
- Auth.js v5 (Credentials provider, JWT sessions)

## Next.js 16 specifics (read before writing App Router code)

This project is on Next.js 16, which changed several conventions from older versions:
- **`middleware.ts` is deprecated in favor of `src/proxy.ts`** (exported function `proxy`, Node.js runtime only — no edge runtime option). Role-guard route protection lives there. Do real DB-backed authorization checks in Server Actions/Route Handlers, not in `proxy.ts` (it runs on every prefetch, so keep it to cheap cookie/JWT checks only).
- **`params` and `searchParams` are `Promise`s with no sync fallback** — always `await` them, in both pages and route handlers: `const { id } = await params`.  Same for `cookies()`, `headers()`, `draftMode()`.
- Turbopack is the default bundler for both `next dev` and `next build`.
- `next.config.ts` is the standard config file format.
- See `AGENTS.md` (auto-regenerated by `next dev` — don't hand-edit) for the upstream reminder to check `node_modules/next/dist/docs/` for anything not covered here.

## shadcn/ui on Base UI (not Radix) — gotchas

This project's shadcn preset (`base-nova`) is built on **Base UI** (`@base-ui/react`), not Radix. Two differences that caused real bugs, both already fixed but worth knowing:
- **Polymorphism uses a `render` prop, not `asChild`.** `<Button asChild><Link .../></Button>` does not exist here — use `<Button render={<Link href="...">label</Link>} />` (children go *on* the render element, not as the Button's children). This applies to `Button`, `SidebarMenuButton`, and any other Base UI primitive wrapper.
- `components/ui/button.tsx` defaults `nativeButton={!props.render}` so `render`-based buttons don't warn about losing native `<button>` semantics — don't remove that default.
- `Accordion` has no `type`/`collapsible` props (Radix concepts); single-open is the default (`multiple` defaults to `false`).

## React Server Component boundary — a real bug we hit

**Never pass a component reference (e.g. a Lucide icon like `LayoutDashboard`) as a prop from a Server Component into a Client Component** — it crashes at runtime ("Functions cannot be passed directly to Client Components"), not at build/type-check time. This bit `DashboardShell`'s nav items: `layout.tsx` (Server Component) was passing `icon: LayoutDashboard` into the client `DashboardShell`. Fixed by rendering the icon into a `React.ReactNode` in the server file (`icon: <LayoutDashboard />`) and passing that instead — a rendered element serializes fine, a bare function reference does not. Same rule applies anywhere else a Server Component passes props into a `"use client"` component.

## Auth.js client `basePath` — must match on both sides

`next-auth/react`'s `SessionProvider`/`signIn`/`signOut` default to fetching `/api/auth/*`, but this app's NextAuth route lives at `/api/v1/auth/[...nextauth]`. Both `NextAuth({ basePath: "/api/v1/auth", ... })` in `src/lib/auth.ts` **and** `<SessionProvider basePath="/api/v1/auth">` in `src/app/providers.tsx` must be set — they're separate bundles (server config vs. client runtime) and neither infers the other's setting. If you ever see `ClientFetchError: Unexpected token '<'` in the browser console, this is almost certainly why.

## `z.coerce.boolean()` footgun with FormData

`z.coerce.boolean()` just calls `Boolean(value)` — `Boolean("false")` is `true` in JavaScript. Any zod schema validating a `FormData`-sourced field (multipart uploads, e.g. `question-bank` create) must NOT use `z.coerce.boolean()` for checkbox/switch fields; use the `booleanField()` preprocessor pattern in `lib/validation/question-bank.ts` instead (checks the string value explicitly). JSON-body routes (PATCH endpoints) are unaffected since `JSON.parse` already produces real booleans.

## Payment provider — read before touching `src/lib/payment/`

**Cashfree is a mock today.** This phase implements only `lib/payment/mock-provider.ts` behind a `PaymentProvider` interface (`lib/payment/provider.ts`), selected via the `PAYMENT_PROVIDER` env var. Real Cashfree integration is a **separate, later plan** — see `docs/HLD.md` § 4. Do not add real gateway calls here unless that follow-up plan is explicitly being executed.

## Conventions

- **Routing**: `(marketing)` and `(auth)` are App Router route groups (organization only, no URL prefix — `/`, `/login`, `/register`). `dashboard/admin` and `dashboard/student` are a real URL segment (`/dashboard/admin/**`, `/dashboard/student/**`) since `src/proxy.ts` needs a real path prefix to match against.
- **API versioning**: all API routes live under `src/app/api/v1/`. Don't add unversioned routes.
- **Feature folders**: domain logic lives in `src/features/<domain>/` (components, hooks, zod schemas). `src/app/**` route files stay thin — they wire a feature into a URL, they don't contain business logic.
- **State**: prefer Server Components/Server Actions first; reach for TanStack Query only for client-side server-state caching, and Zustand only for genuinely client-side UI state (checkout steps, multi-step forms). Auth state comes from `next-auth`'s `useSession`, never a duplicate store.
- **Money**: all prices stored as integers (paise), never floats.
- **File security**: the original uploaded PDF, the generated preview, and invoices are stored on Cloudinary as `type: authenticated` raw resources — never publicly reachable. They are only ever fetched server-side (signed URL) and streamed through the authenticated `/api/v1/files/**` routes, which keep their session/ownership checks. Preview files are separately generated, capped copies. Downloads are watermarked in memory at request time — never persisted watermarked. Thumbnails are the one public asset (the catalog is public) and are served directly from the Cloudinary CDN.

## Environment variables

See `.env.example` for the full list. Key ones:
- `DATABASE_URL` — Postgres connection string
- `NEXTAUTH_SECRET`, `NEXTAUTH_URL` — Auth.js
- `ADMIN_EMAIL`, `ADMIN_PASSWORD` — used once by `prisma/seed.ts` to create the single admin account
- `PAYMENT_PROVIDER` — `mock` for now; `cashfree` reserved for the follow-up plan
- `RESEND_API_KEY`, `EMAIL_FROM` — Resend, used for password-reset + contact-form emails (`EMAIL_FROM` must be on a Resend-verified domain)
- `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET` — Cloudinary account used by `src/lib/storage.ts` for all uploaded files, previews, thumbnails, and invoices
- `MAX_UPLOAD_MB` — max question-bank upload size
